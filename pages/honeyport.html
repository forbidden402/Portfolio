01

Architecture & Deception Mechanics

The core defensive principle of Honeyport is simple: real services carry real risk, while fake services collect pure intelligence. Honeyport runs entirely as an unprivileged process listening on ports above 1024. In production environments, standard service ports (22, 80, 21, 23) can be redirected to these listeners via firewall NAT rules.

Every listener operates as a standalone threaded TCP socket server that simulates service handshakes and captures interaction payloads without executing arbitrary code or forwarding traffic:

Service Port Emulated Behavior & Interaction Trap Forensic Data Logged
Fake SSH 2222 Sends realistic OpenSSH banner, accepts client version string and protocol handshake. Client software version, raw SSH payload, timestamp, source IP/port.
Fake HTTP 8080 Renders an administrative gateway login page; accepts and parses authentication attempts. Submitted usernames, passwords, HTTP User-Agents, request URIs, headers.
Fake FTP 2121 Simulates FTP server greeting; responds with RFC-compliant prompts to USER and PASS commands. Captured plaintext credentials, anonymous login attempts, probe sequences.
Fake Telnet 2323 Emulates legacy embedded terminal challenge; prompts for username and login passwords. Automated botnet brute-force dictionaries, default credential sweeps.
Sensor & SIEM Architectural Separation

Following production security engineering practices, listeners strictly write events into the SQLite data tier, while the Flask API and frontend dashboard only execute read queries. This strict unidirectional boundary ensures that sensor ingestion performance and dashboard interactions remain completely isolated.

02

Automated Threat Intelligence Enrichment

When an external IP triggers a listener trap for the first time, Honeyport dispatches an asynchronous background worker to enrich the event across three distinct threat intelligence providers, turning opportunistic scanner encounters into actionable SOC indicators:

  • AbuseIPDB: Checks historical reputation, community reports, confidence scores, and ISP network ownership.
  • VirusTotal: Queries multi-vendor security engine detections associated with the attacker's origin address.
  • Shodan: Turns the tables by scanning the attacker IP's own open ports, exposed vulnerabilities, and running software banners.

Defensive API Architecture: Each external API call is wrapped in strict timeout protections and error handlers. Missing API keys, network dropouts, or exceeded quota limits gracefully downgrade to an unavailable status in the UI, ensuring third-party dependencies never block event ingestion or crash the application.

Quota Preservation Caching

Enrichment responses are cached in a dedicated SQLite table for 6 hours. Repeat probes from high-volume automated scanners reuse cached intelligence, preserving API limits while maintaining responsive dashboard telemetry. Private and loopback IPs (RFC 1918) bypass external lookups automatically.

03

MITRE ATT&CK Mapping & Abuse Detection

Every security event is evaluated against a deterministic local MITRE ATT&CK technique lookup table. Because the mapping is evaluated locally in-process without network calls, tagging is instantaneous and immune to external service outages:

  • T1110 (Brute Force): Triggered by repetitive credential attempts across SSH, FTP, Telnet, or HTTP POST handlers.
  • T1046 (Network Service Discovery): Correlated when single IP sources probe multiple distinct ports in rapid succession.
  • T1078 (Valid Accounts): Flagged during dictionary sweeps attempting common default administrative credentials.

A sliding-window abuse counter actively tracks hit rates per source IP. When interaction frequency exceeds configured thresholds (e.g. 10 hits within a 60-second window), the IP is flagged with an abuse badge on the dashboard, signaling an indicator ready for automated firewall drop rules or SIEM blocklisting.
