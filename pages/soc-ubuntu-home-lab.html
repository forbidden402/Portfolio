The offensive phase simulated a complete intrusion lifecycle: active service scanning, targeted dictionary brute-forcing, interactive session establishment, backdoor local user creation, sudoers privilege escalation, and upgrading to a Meterpreter C2 channel.

Part 2 · Layer 1: Network Traffic Analysis (Wireshark)

During the attack, I captured traffic on the target interface (ens33) into ssh_wireshark.pcapng and examined the capture in Wireshark.

What Wireshark Revealed (Packet Analysis Results)
  • Connection Flood: A rapid flood of TCP three-way handshakes to port 22 initiated by 192.168.133.142.
  • Ephemeral Port Velocity: Multiple ephemeral source ports opening short-lived TCP streams in quick succession—a clear footprint of automated brute-force tools.
The Critical Limitation of Network-Only Inspection

Because modern SSH uses encrypted payloads after the initial handshake, Wireshark could not reveal usernames, attempted passwords, or executed commands. Network traffic confirmed when and from where connections occurred, but host-level visibility was required to understand the true impact.

05 DETECT · LAYER 3

Part 2 · Layer 3: Centralized Threat Hunting (Splunk Enterprise)

On the Windows 11 host, I opened Splunk Enterprise to query the forwarded dataset (index=main host="ubuntu") and build actionable SPL threat hunts.

Search 1: Extracting Attacker IP and Session Ports with rex

Because /var/log/auth.log is unstructured text, fields like source IP and ephemeral port are not indexed out of the box. I wrote a regular expression with Splunk's rex command to parse these fields on the fly:

SPL Hunt 01 · Accepted Logins & rex Extraction
index=main host="ubuntu" source="/var/log/auth.log" "accepted" | rex field=_raw "from (?<src_ip>\d+\.\d+\.\d+\.\d+) port (?<port>\d+)" | table _time, src_ip, port, _raw | sort - _time
Forensic Evidence Uncovered (Search 1 Results)
  • 33 total events matched in the 24-hour investigation window.
  • Single Source IP: Every single authenticated session originated from src_ip = 192.168.133.142 (the Kali attacker).
  • Ephemeral Port Sequencing: The query captured connections across 10 distinct source ports (44785, 53092, 33673, 37447, 54530, 33568, 39540, 33505, 51518, 50244), correlating directly with each new SSH session opened during the attack.

Search 2: Hunting Account Creation (new user / useradd)

To detect potential backdoor accounts, I searched for user creation activity across the logs:

SPL Hunt 02 · User Creation Detection
index=main host="ubuntu" source="/var/log/auth.log" (new user OR useradd) | table _time, _raw
Forensic Evidence Uncovered (Search 2 Results)
  • Returned 91 events total. While much of this included background noise from systemd-logind session lifecycle events (class 'user', type 'wayland', type 'tty'), filtering by useradd pinpointed the malicious account creation:
auth.log · Isolated useradd Provisioning Event RAW SYSLOG
2026-10-02T17:51:22.900911+05:30 ubuntu useradd[5673]: new user: name=hacker, UID=1002, GID=1002, home=/home/hacker, shell=/bin/sh, from=/dev/pts/3 2026-10-02T17:51:22.892929+05:30 ubuntu useradd[5673]: new group: name=hacker, GID=1002

This proved that a brand-new local account (hacker) was provisioned directly from an interactive pseudo-terminal (/dev/pts/3) shortly after the initial SSH compromise.

Search 3: Tracking Group Membership & Privilege Escalation

Next, I hunted for group modifications to see if any accounts were being elevated to administrative groups:

SPL Hunt 03a · Baseline vs. Malicious Group Modifications
index=main host="ubuntu" source="/var/log/auth.log" (add member OR to group) | table _time, _raw
Baseline vs. Malicious Findings (Search 3a Results)
  • Returned 12 events total.
  • Splunk surfaced both legitimate baseline setup activity (add 'ubuntu' to shadow group 'wireshark' at 10:13:58) and the attack activity (add 'hacker' to group 'sudo').

To focus purely on the intruder's account, I filtered directly on the username hacker:

SPL Hunt 03b · Isolated Privilege Escalation to Sudo

Key Findings & Investigation Takeaways

  • Weak passwords break perimeter defenses in seconds: Simple dictionary lists cracked ubuntu:sudosu near-instantly. Mandatory public-key authentication (disabling password authentication in sshd_config) is non-negotiable.
  • Built-in OpenSSH rate-limiting is not a replacement for active banning: Modern Ubuntu OpenSSH implements srclimit_penalise (17-second progressive delay), but does not ban offending IPs permanently. Automated tools like Hydra easily absorb these delays and eventually compromise the system. Active tooling like Fail2ban or firewall rate-limiting is required.
  • Packet captures and host logs must be correlated: Wireshark captures traffic volume and connection velocity, but payload encryption blinds analysts to command execution. Endpoint syslog telemetry (auth.log) is required to understand true operational impact.
  • Dynamic regex parsing (rex) is essential for unstructured text logs: Unstructured log lines require flexible SIEM parsing. Splunk's rex command allows tier-1 analysts to extract ad-hoc fields on the fly without waiting for pipeline schema re-indexing.
  • User creation combined with sudo elevation is a critical attack signal: Any occurrence of useradd immediately followed by usermod -aG sudo within an active remote SSH session warrants immediate high-priority SOC escalation.

Detection Engineering & Production SIEM Rules

Actionable, high-fidelity detection rules developed from this lab exercise ready for deployment into enterprise SOC SIEM environments:

1. SSH Brute-Force Activity (High Frequency)
index=* source="/var/log/auth.log" "Failed password" | rex field=_raw "from (?<src_ip>\d+\.\d+\.\d+\.\d+)" | stats count by src_ip | where count > 10
2. Privilege Escalation to Sudo Group
index=* source="/var/log/auth.log" ("add member" OR "to group") AND ("sudo" OR "wheel" OR "admin") | table _time, host, _raw
3. Suspicious New User Creation
index=* source="/var/log/auth.log" "useradd" "new user:" | rex field=_raw "name=(?<created_user>\w+)" | table _time, host, created_user, _raw
4. Repeated Failed su Attempts
index=* source="/var/log/auth.log" "FAILED SU" | stats count by host, _raw
